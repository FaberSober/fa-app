# ADR：fa-im 租户隔离与分租户未读消息

- 状态：🕒待处理
- 日期：2026-09-16
- 范围：`fa-im`，依赖现有 `fa-base` 租户上下文和用户租户权限

## 背景

当前 `fa-im` 的未读数接口按用户汇总，`im_conversation`、`im_message`、`im_participant` 等消息表没有明确的 `tenant_id`。现有自定义 Mapper SQL 也没有统一显式带租户条件，因此无法安全地为 mobile 展示“每个租户独立的未读消息数”。

## 目标

- 为 IM 会话、消息和参与人建立明确的租户归属。
- 保证会话、消息、未读数、已读状态等查询和写入都在租户范围内执行。
- 提供当前用户所有有效租户的未读数聚合接口。
- 兼容现有单租户调用方式，并为历史数据提供可执行的迁移策略。

## 范围边界

- 本文负责 `fa-im` 的数据模型、SQL、接口和实时事件租户隔离。
- mobile 的工作空间 UI、租户切换和客户端状态由 [mobile 多租户工作空间 ADR](2026-09-16-mobile-multi-tenant-switch.md) 负责。
- 不在本期实现租户创建、成员邀请和跨租户消息互通。

## 决策

### 1. IM 数据按租户隔离

- 至少为 `im_conversation`、`im_message`、`im_participant` 增加 `tenant_id`；建议 `im_message_read` 同步保留该字段，便于完整校验和索引。
- 所有 IM 写入从服务端当前租户上下文获取 `tenant_id`，不信任客户端直接传入的租户 ID。
- 同一用户在不同租户中的会话、消息和未读数相互独立。
- 单聊会话的唯一键调整为租户内唯一，例如 `(tenant_id, single_key)`。

### 2. 显式执行租户过滤

- 会话、消息、参与人、已读状态和未读数相关 SQL 都必须显式带 `tenant_id` 条件。
- 重点审查并调整 `listQuery`、`countUnreadByUserId`、会话参与人查询、未读数更新和消息列表查询。
- 业务 SQL 继续写在 Mapper XML 中，不使用 Mapper 注解 SQL。
- 当前租户请求仍通过 `fa-tn-tenant-id` 进入后端，并由现有租户权限机制校验。

### 3. 增加跨租户未读数聚合接口

新增接口：

```text
GET /api/im/core/imConversation/unreadByTenants
```

返回示例：

```json
[
  {
    "tenantId": "tenant-a",
    "unreadCount": 12
  },
  {
    "tenantId": "tenant-b",
    "unreadCount": 0
  }
]
```

接口约定：

- 服务端根据当前用户的有效租户关系生成查询范围。
- 客户端不能通过传入任意租户 ID 获取其他租户的未读数。
- 0 未读的租户也返回，方便客户端稳定合并列表。
- 使用按 `tenant_id` 分组的一次查询，避免 mobile 按租户循环请求。
- 现有 `getUnreadCount` 保留为当前租户未读数接口，语义调整为当前租户范围内统计。

### 4. 跨租户查询使用受控范围

- 聚合接口需要查询用户所有有效租户，不能简单依赖单个当前租户上下文。
- 接口仍必须经过登录校验和租户成员关系校验。
- 如果现有拦截器只支持单租户上下文，应增加明确的“当前用户所有授权租户”服务范围或接口标记，不采用关闭鉴权的方式绕过租户校验。
- 服务端最终使用已校验的租户 ID 集合执行分组查询。

### 5. 历史数据迁移

- 开发前确认现有 IM 数据是归属默认租户、指定租户，还是需要作为全局历史数据保留。
- 推荐分阶段迁移：先增加字段和索引，再按确认策略回填，最后在允许的表上收紧非空约束。
- MySQL 与 PostgreSQL 的 DDL、升级 SQL 分目录提供，使用各自数据库方言；已发布脚本不改写。
- 在数据归属未确认前，不直接把全部历史数据按当前用户或当前默认租户批量回填。

### 6. 实时事件携带租户标识

- 后续 IM WebSocket 的新消息、已读和未读变化事件需要携带 `tenantId`。
- mobile 根据事件只更新对应工作空间的角标。
- WebSocket 重连后重新执行一次全量聚合查询，修正本地计数。
- 实时角标作为第二阶段能力，本期先保证主动刷新结果正确。

## 数据与接口说明

### 相关数据字段

```text
tenant_id  当前 IM 数据所属租户
```

建议为租户字段和常用查询字段建立组合索引：

- `im_participant(tenant_id, user_id)`
- `im_participant(tenant_id, conversation_id)`
- `im_conversation(tenant_id, id)`
- 消息列表使用的 `(tenant_id, conversation_id, created_time)`

具体索引名称和字段顺序以现有 DDL、查询计划及目标数据库为准。

### 未读数统计

未读数按租户、用户汇总参与人表中的 `unread_count`，并只统计未删除会话。返回数据至少包含：

- `tenantId`
- `unreadCount`

## 开发说明

### 数据库与实体

- 为消息相关表增加租户字段、索引和租户内唯一约束。
- 同步 Java Entity、Mapper 参数和数据库升级脚本。
- 分别验证 MySQL 与 PostgreSQL 脚本，不混用数据库方言。

### 消息写入与查询

- 创建会话、发送消息、创建参与人和更新未读数时写入当前租户。
- 所有自定义 XML SQL 增加租户条件和必要的租户参数。
- 验证同一用户在不同租户下的数据不会互相读取或更新。

### 未读数接口

- 增加按租户分组的 Mapper 查询、Biz 方法和 Controller 接口。
- 服务端自行获取用户有效租户范围，禁止使用客户端未校验的租户列表。
- 保留当前租户未读数接口，明确其统计范围。

### 迁移与验证

- 按确认的历史数据策略执行回填和兼容处理。
- 验证单租户、多租户、租户失效、越权访问和历史数据场景。
- 验证聚合接口查询次数、索引命中情况和大数据量下的响应时间。

## 实施顺序

1. 确认历史 IM 数据的租户归属策略和 `fa-im` 支持的目标数据库。
2. 增加 IM 表租户字段、索引和租户内唯一约束。
3. 更新 Entity、写入链路和消息相关 Mapper XML。
4. 调整会话、消息、参与人、已读和未读数查询的租户过滤。
5. 将现有当前租户未读数接口限定为当前租户范围。
6. 增加跨租户未读数聚合接口并完成权限校验。
7. 按迁移策略回填历史数据，验证升级和回滚预案。
8. 评估并实现带 `tenantId` 的 WebSocket 事件，作为后续版本能力。

## 兼容与发布策略

- 先发布数据库字段和兼容代码，再启用严格租户过滤和聚合接口。
- 数据迁移完成前，禁止把未归属数据错误展示到任意租户。
- 接口失败时 mobile 保留上次未读数并允许重试，不影响登录和当前租户业务访问。
- 旧客户端只发送当前租户请求头时，仍可访问当前租户范围内的 IM 数据。

## 验收标准

- 所有新建 IM 数据都有正确的 `tenant_id`。
- 同一用户在租户 A 的会话和消息不会出现在租户 B。
- 当前租户未读数只统计当前租户数据。
- 跨租户聚合接口一次返回所有有效租户的未读数，包含 0 未读租户。
- 非成员不能通过请求头或聚合接口读取其他租户数据。
- 会话创建、消息发送、已读和未读更新均不会跨租户操作。
- 历史数据按确认的策略完成迁移，且迁移过程可审计。
- MySQL 与 PostgreSQL 的脚本分别通过对应数据库验证。
- WebSocket 事件具备租户标识后，客户端能够只更新对应租户角标；未完成实时能力时不影响主动刷新方案。
