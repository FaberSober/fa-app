# ADR：fa-app 应用版本管理与 Uni-app 增量发布

- 状态：🟡进行中
- 日期：2026-09-16
- 范围：`fa-app` 后端、`mobile` Uni-app 客户端

## 背景

`fa-app` 当前已经具备 APK 应用管理、版本记录、文件上传、最新版本查询和下载能力，但模型和接口仍以 APK 为中心，不能完整支持 Uni-app 的多平台发布及 APP-PLUS WGT 增量更新。

## 目标

- 保留现有 APK 管理能力，修正已发现的版本和数据一致性问题。
- 增加统一的应用发布模型，支持 Android、iOS、APP-PLUS、微信小程序和 H5 的发布信息。
- 为 APP-PLUS 提供 WGT 增量包检查、下载、校验和安装流程。
- 明确原生包、WGT、小程序和 H5 的更新边界，避免把不同平台的发布方式混在一起。

## 决策

### 1. 后端模型

保留现有 `app_apk`、`app_apk_version`，兼容已有 APK 管理和接口；新增通用发布模型：

- `app_release`：应用版本、发布状态、渠道、最低支持版本、更新说明、强制更新和发布时间。
- `app_release_package`：平台、包类型、文件 ID、文件大小、SHA-256、WGT 基准版本等实际发布包信息。

关键字段约定：

- `versionCode` 使用 Java `Long`，数据库使用 `bigint`。
- 发布状态至少包括草稿、已发布、已撤回。
- 平台包括 `ANDROID`、`IOS`、`APP_PLUS`、`MP_WEIXIN`、`H5`；包类型包括 `APK`、`IPA`、`WGT`、`FULL`。
- WGT 必须记录 `baseVersionCode`；原生代码、权限、原生插件或启动配置变化必须发布完整 APK/IPA。
- MySQL 与 PostgreSQL 分别提供等价 DDL，遵循各自目录和方言规范，不使用跨库混写。

不实现自定义二进制 diff 算法，Uni-app APP-PLUS 直接使用官方 WGT 作为增量资源包。

### 2. 版本检查接口

新增无需登录的公开检查接口，例如：`POST /api/app/app/release/check`。

请求至少包含：`appCode`、`platform`、`currentVersionCode`、`channel`。首期 `appCode` 映射现有 `app_apk.short_code`。

响应至少包含：

- 是否有更新、更新类型（`NONE`/`WGT`/`FULL`）。
- 目标版本号、版本名、基准版本号、最低支持版本和强制更新标记。
- 文件 ID、下载地址、大小、SHA-256 和更新说明。

版本选择规则：

- 只返回已发布且未撤回、匹配应用/平台/渠道的版本。
- 只选择大于客户端当前 `versionCode` 的版本。
- APP-PLUS 优先匹配当前版本的 WGT；没有匹配 WGT 时回退到完整包。
- 客户端低于最低支持版本时，返回强制完整包更新。
- `appCode` 仅作为公开定位标识，不作为密钥；现有短码不承担鉴权职责。

### 3. mobile 客户端分层

按照“Core 放基础能力、Base 做业务集成”的约定实现：

- `fa-core-mobile`：版本读取、检查请求抽象、下载、SHA-256 校验、安装、幂等锁、结果状态和失败保护。
- `fa-base-mobile`：注入当前应用的 `appCode`/渠道，封装发布接口，提供更新弹窗、强制更新和更新说明交互。
- 业务 Feature 只调用 Base 暴露的更新能力，不直接操作 WGT 安装 API。

客户端流程：启动或进入前台 → 读取当前版本 → 请求检查 → 展示更新信息 → 下载 → 校验摘要 → 安装并重启。下载、校验或安装失败时保留当前版本，不阻断正常业务。

### 4. 平台边界

- APP-PLUS Android/iOS：支持 WGT 增量资源更新；涉及原生能力时改用 APK/IPA 完整更新。
- 微信小程序：不接入 WGT，按小程序平台审核和发布流程更新。
- H5：使用静态资源/CDN 发布、缓存控制和回滚，不走客户端 WGT 安装。
- 灰度发布、设备范围、复杂渠道规则和自动回滚先不作为首期必需能力；首期支持渠道字段和服务端撤回。

## 对现有 APK 模块的修正要求

- 最新版本不能只按数据库主键排序，应按已发布状态和 `versionCode` 选择。
- 创建应用及其首个版本需要事务，避免主表成功而版本历史保存失败。
- 增加版本号重复、递增和文件信息校验。
- 修正无版本数据时的空值处理。
- 复核应用短码和应用关联查询的唯一性判断，避免误判重复数据。
- 公共最新版本和下载接口继续兼容，新增通用发布接口不直接破坏旧接口。

## 实施顺序

1. 修正现有 APK 管理的数据一致性和版本选择逻辑。
2. 新增 `app_release`、`app_release_package` 实体、Mapper、业务层、Controller 及 MySQL/PostgreSQL DDL。
3. 实现发布状态、渠道、最低支持版本、强制更新和撤回能力。
4. 实现公开版本检查和下载信息返回，补充版本选择测试。
5. 接入 APP-PLUS WGT 上传、发布和摘要校验。
6. 在 `fa-core-mobile` 实现更新基础能力，在 `fa-base-mobile` 接入业务交互。
7. 联调完整包回退、WGT 基准版本不匹配、撤回和失败恢复场景。

## 验收标准

- 现有 APK 上传、历史查询、最新版本和下载流程保持可用。
- 同一应用、平台、渠道下，版本选择结果稳定且不会返回草稿或撤回版本。
- APP-PLUS 当前版本存在匹配 WGT 时返回 WGT，否则返回完整包。
- WGT 摘要校验失败不会安装，客户端仍可继续使用当前版本。
- 原生变更不会误标为 WGT 更新。
- MySQL 和 PostgreSQL DDL 可分别执行，字段类型与 Java 实体一致。
- 小程序和 H5 更新策略有明确的非 WGT 处理路径。
