## 功能开发说明

1. **发布模型与接口**：沿用 `app_apk` 标识应用、`app_release` 管理版本、`app_release_package` 管理包。后端已有 `uploadWgt`、`publish`、`revoke` 和公开 `check` 接口，本期以真实发布流程验证其可用性。
2. **多基准 WGT 约束**：当前业务层按 `baseVersionCode` 判重，但 MySQL/PostgreSQL 唯一键只包含发布 ID、平台和包类型。用两库新版本迁移脚本调整约束，兼顾非 WGT 包唯一性和软删除记录；不改已发布的 `1.0.6` 脚本。
3. **上传与管理接口补齐**：核对文件上传失败后的记录一致性、大小限制和摘要校验；确认包列表能按 `releaseId` 服务端过滤，并受管理权限控制。
4. **类型与服务**：在 `fa-app-pages` 增加发布记录、发布包类型及 API service。`Long` 版本编码在前端按字符串处理，避免数值精度问题。
5. **版本维护页面**：在现有 APP 列表增加“版本发布”入口，复用 Desktop 版本页的列表交互。草稿可编辑；已发布和已撤回只读。发布前展示版本、渠道、包和灰度信息供确认。
6. **WGT 上传入口**：草稿下填写基准版本并上传 `.wgt`；文件大小和 SHA-256 由后端返回。成功后刷新包列表，失败时保留输入；不同基准版本可分别上传。
7. **菜单与权限**：优先复用 APP 管理页面；按现有 RBAC 方式补齐入口和操作权限，所需 SQL 同时提供 MySQL、PostgreSQL 版本。
8. **发布联调**：用测试 APP 验证草稿 → 上传 → 发布 → 客户端检查/安装 → 撤回，并覆盖基准版本不匹配、摘要错误和上传失败。

## 背景与决策

[ADR-app-002](ADR-app-002-app-release-and-uniapp-incremental-update.md) 曾将“APP-PLUS 包发布”标为已完成。核对发现后端已有上传和发布逻辑，但管理端只有旧 APK 页面和 Desktop 发布页面，缺少 `app_release` 的维护页、WGT 上传入口及菜单，因此发布闭环仍未完成。

本期在现有 APP 管理页增加版本发布入口，沿用通用发布模型；旧 APK 页面与接口继续保留。暂不开发 WGT 构建流水线、小程序/H5/Desktop 发布页面或新的 mobile 更新引擎。完整包上传需先明确文件来源及各平台安装方式，留作后续规划。

## 验收标准

- 管理员无需手工调用 API，即可创建草稿、上传 WGT、查看包信息、发布和撤回。
- 同一目标版本可保存不同基准版本的 WGT；重复基准版本有明确提示，MySQL/PostgreSQL 行为一致。
- 非草稿不能修改包；文件缺失或摘要不符时不能发布；失败上传不留下可发布的残缺记录。
- 客户端获得匹配基准版本的 WGT；不匹配时按 ADR-app-002 规则回退完整包；撤回后不再下发。
- 管理操作受权限控制，旧 APK 流程保持可用。

需要人工验证的功能在开发后标为 `🔍验证中`；经用户确认“验证成功”后改为 `✅已完成`。可自动完成验证的功能直接标为 `✅已完成`。全部功能完成后同步更新 ADR-app-002。
